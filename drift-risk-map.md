### Coupling mechanism legend

- **codegen**: Dependent is machine-generated from the source. Stays in sync
  if the generation step runs.
- **shared-import**: Dependent imports types/values directly from the source
  module. Compiler/interpreter enforces the contract.
- **manual-mirror**: Dependent restates information from the source by hand.
  No automated enforcement.
- **contract-test**: A dedicated test asserts agreement between source and
  dependent.
- **lint-rule / build-step / runtime-validation / none**: as named.

### Propagation mode legend

- **build-error** → **type-error** → **test-failure** → **lint-failure** →
  **runtime-error** → **silent**, ranked loud to quiet. **silent** means the
  dependent artifact is now wrong and nothing signals it.

**Guard**: ⚠ NONE. `agent_memory`'s own record concedes it:
`"note": "The source is external to this repository; --check runs only where
it is checked out."`

**How drift manifests**: `plugins/loop_forward/README.md` states that the
vendored copy's digest is recorded "so a copy that has drifted from its source
is a checkable fact rather than a discovery." It is not checkable in CI: the
source path is git-ignored, so on a fresh clone the file named as the source
of truth is simply absent. If the canonical contract gains a field — say a new
`lf:StopCondition` arm — the plugin's profile continues to validate writes
against the old shape, `npm run check` passes on every platform in the matrix,
and the divergence is discovered only when a document authored against the new
contract is rejected by the old profile. I verified all three copies are
byte-identical to their sources **on this machine today** (`diff -q` clean,
recorded sha256 matches recomputation). That consistency is a property of this
checkout, not of the repository.

**Recommended fix**: Make the source reachable, then check it. Two steps:
(a) Track the canonical schemas — move `_ingest_bin/*.schema.ts` to a tracked
path (`static/schemas/` already serves this role for three other plugins) and
drop it from `.gitignore`. For `agent_memory`, vendor the source file itself
alongside `vendored_from_digest` rather than naming a machine path.
(b) Add `tests/_meta/vendored-schema-drift.test.ts` that, for every
`plugins/*/generated/schema-hash.json`, recomputes sha256 over each entry in
`files` and asserts equality — the check `acme_business_deck` and
`acme_pitch_deck` already perform, generalised over the directory listing so
new plugins are enrolled automatically. Where `vendored_from` resolves in the
tree, assert the source digest too. It runs in `npm test`, so it lands in the
existing CI `test` job with no workflow change.

### Finding #3: `docs/specs/SPEC-*.md` is never compared to its generator

**Source**: `fdpm-cli/scripts/build-spec-*.ts` — 11 scripts
(`build-spec-core`, `-cel-validator`, `-dnis`, `-document-plan`,
`-expression-runtime`, `-mcp-server`, `-render-dsl`, `-repl`,
`-sections-tree`, `-uid`, `-workspace`).
**Dependent**: the 11 committed `docs/specs/SPEC-*.md` documents.
**Mechanism**: codegen — but the generation is a two-command manual ritual
documented in each script's header:

```
FDPM_DATA_DIR=/tmp/fdpm-spec-mcp npx tsx fdpm-cli/scripts/build-spec-mcp-server.ts
FDPM_DATA_DIR=/tmp/fdpm-spec-mcp npx tsx fdpm-cli/src/bin/fdpm.ts \
  render spec-mcp-server text/markdown \
  --renderer-id spec:SpecMarkdownRenderer -o docs/specs/SPEC-MCP-SERVER.md
```

**Guard**: ⚠ NONE for content. `tests/spec-builds-determinism.test.ts` covers
`SPEC-EXPRESSION-RUNTIME`, `SPEC-RENDER-DSL` and `SPEC-DOCUMENT-PLAN`, and
asserts three things — the build validates with zero findings, it renders
byte-identically across two fresh data dirs, and the rendered text mentions
every shared constant. It renders into a temp dir and compares the render to
*another render*. `docs/specs/` is never read. The remaining eight scripts
have no test.

**How drift manifests**: a developer edits `build-spec-mcp-server.ts` to add a
tool-class definition and forgets the second command. `npm run check` passes:
the script still builds, still validates, still renders deterministically. The
committed SPEC — the document `CLAUDE.md` treats as normative and that other
SPECs cross-reference — now describes a system that the generator no longer
describes. Nothing in the repository can tell the two apart.

I regenerated `SPEC-MCP-SERVER.md` end-to-end and diffed it against the
committed file: **802 lines each, byte-identical**. The coupling is unguarded
and currently in sync. That is the good case, and it is indistinguishable from
the bad case without running the regeneration by hand.

**Recommended fix**: Give every spec builder the `--check` mode that
`build-arch-census.ts`, `build-profile-atlas.ts` and `build-env-docs.ts`
already implement — build into a temp data dir, render in memory, compare to
the committed `docs/specs/SPEC-*.md`, exit non-zero on difference. Then add
one parametrised case per script to `tests/_meta/doc-drift.test.ts`,
enumerating `scripts/build-spec-*.ts` by glob so a new spec builder is
enrolled the day it is written. Budget: the three existing builds take ~10 s
each, so all eleven is roughly two minutes — appropriate for the `test` job,
and cheap next to the 45-minute timeout already allowed.

### Finding #4: `GENERATOR.md` declares itself the source of truth; nothing reads it

**Source**: `plugins/knowledge_cartridge/GENERATOR.md:11-20`, whose header
comment states: *"ids.ts transcribes this file's vocabularies (the six probes,
the four source tiers, the four corpus defects), primitives.ts transcribes its
Pass-5 layer contracts, and validators.ts implements nine of its eleven Pass-6
checks. Where a plugin source and this document disagree, this document is
right and the plugin is a bug."*
**Dependent**: `plugins/knowledge_cartridge/ids.ts` (`PROBE`, `SOURCE_TIER`,
`DEFECT_KIND`, `FINDING_GRADE`, `SUBSTRATE`), `primitives.ts` (layer field
contracts), `validators.ts` (`RULE`, `KC_UNENFORCEABLE_CHECKS`).
**Mechanism**: manual-mirror.
**Guard**: ⚠ NONE. Six test files cite `GENERATOR.md` — all in prose comments.
The only `readFileSync` in the suite (`prompts.test.ts:46`) walks the *plugin
source* collecting `kc:` ids; it never opens `GENERATOR.md`.

**How drift manifests**: the document defines the closed vocabularies as
tables. An editor renames the `preference` probe to `comparison` in the Pass-2
table. `ids.ts` still exports `preference`; the profile still accepts
`preference`; every test passes. The document is now, by its own rule,
correct — and the plugin is, by its own rule, a bug that nothing detects. The
same applies to the eleven-item Pass-6 checklist, of which `validators.ts`
implements nine and declares two structurally unenforceable: no test asserts
that 9 + `KC_UNENFORCEABLE_CHECKS.length` equals the number of checklist items
in the document.

I compared the current transcription by hand — the six probes, four tiers,
four defect kinds, two grades and four substrates in `ids.ts` all match
`GENERATOR.md`. Consistent today, unenforced.

**Recommended fix**: Parse the document in a test. `GENERATOR.md`'s
vocabularies live in Markdown tables and a fenced block with stable shapes, so
a ~40-line `tests/plugins/knowledge_cartridge/generator-parity.test.ts` can
extract the Pass-2 probe column, the Pass-1 tier list, the §4 defect table and
the Pass-6 checklist items, and assert set-equality against `PROBE`,
`SOURCE_TIER`, `DEFECT_KIND` and `RULE ∪ KC_UNENFORCEABLE_CHECKS`. This is the
same technique the loop-forward prompt drift gate already uses in the other
direction, and it makes the document's stated precedence rule executable
instead of aspirational.

### Heuristic limitations

This analysis is based on static file-pattern matching (`grep`, `find`,
`diff`, targeted file reads) plus four executed verification commands. It
cannot detect:

- Couplings mediated by runtime reflection or metaprogramming — relevant here,
  since plugin capabilities are registered dynamically at activation.
- Couplings that exist only across repository boundaries unless all repos are
  present. Finding #1 is precisely such a case, detected only because the
  *record* of it is in-tree.
- Semantic equivalence — two definitions may look different and be logically
  identical (as in Finding #2) or look similar and diverge in meaning.
- The completeness of any test suite. A "test-failure" propagation mode
  assumes the relevant test exists **and** covers the relevant path; I read
  each cited test's assertions, but not every branch it exercises.
